## Working conventions

- The new kernel is module `Features` in `Packages/AppComposition` while the first kernel (`Composition`) still serves the app that has not migrated. Work item 8 deletes the first kernel and gives the new one the `Composition` name, so RelayBar's Xcode project needs no package-product change.
- `PreviewSupport` no longer depends on a kernel type: a registration returns a handle, and a thin adapter ties it to a feature's scope. `PreviewRegistry+Legacy.swift` is the first kernel's adapter and goes with it.

## Progress

- **Work 1, kernel.** `Features` adds `ServiceKey`, `Feature`, `@Need`/`@Offer`/`@Constant`, `FeatureNode` with a result builder and realms, `FeatureRuntime`, `FeatureContext`, `ServicePort`, a labelled `EffectScope` and `PreferenceStore`. 42 tests pass with warnings as errors: 26 runtime (the eight audit probes plus the ported ordering, rollback, realm, cycle and convergence cases), 6 scope, 6 preferences, 4 preview-registry and fixture. The first kernel's 37 tests still pass.
- A feature withdrawn while it is still loading keeps its scope open until `run` returns, so a resource acquired late can still register its undo; `isActive` reports false meanwhile and the undo runs as soon as `run` returns.
- **Work 2 and 3, RelayBar.** RelayBar now runs on `Features`. Its tree is decided in one `tree()` function from the preference document and whether the Remote Files window is open: `tunnels`, `tunnels.retry-limit`, `updates`, `updates.schedule`, `login`, `frame.host`, and `remote.files` with one child per enabled preview format plus `open-in-frame`. Profiles and groups are no longer features; `TunnelStore` is their only owner and `TunnelProfileRuntime` has no second activation path. Browser opening and the server catalog are injected values. `RemotePreviewPlugins` has no nested runtime. Preferences are `preferences.json` (`RelayBarPreferences`: retry limit, automatic update checks, per-format overrides), imported once from `sshRetryLimit.v1` and `SUEnableAutomaticChecks`. The retry limit and update schedule are applied by two features whose configuration is the setting. A failed or stuck feature is reported once through the existing alert with its id and reason. Quit uses a 20-second bounded shutdown.
- RelayBar suite after the migration: 384 tests, 27 optional skips, zero failures, warnings as errors (`.build/task-059-relaybar.log`). Rewritten suites: composition (5 tests, including newer-version preferences and a failing feature) and tunnel composition (8 tests, including starting a tunnel while the Remote Files window is still unloading). Frame, still on the first kernel, passes its 163 tests against the changed shared package (`.build/task-059-frame-pre.log`).
- **Work 4 to 6, Frame.** Frame now runs on the new kernel. `relay.link` is one feature that owns discovery and the session and fills or clears the `RelaySession` slot; `FrameRemoteLink` no longer has a transition queue, a visibility service or outside activation, and the six relay entries (four of them empty markers) are gone. Slot withdrawal is synchronous in the kernel, so a consumer needs one liveness check where it previously re-resolved each capability. `Slot.drained()` lets the link release an ended session's client only after everything that used it has unloaded. Thumbnails, metadata, the preview host, the preview formats and video playback are each one definition mounted at the root and again in the `remote` realm, which isolates `MediaSource`, `Thumbnails`, `Metadata`, `Previews` and `PlaybackPreviews`. The player and document renderer stay shared. Preferences are `preferences.json` (`FramePreferenceDocument`), imported once from UserDefaults; the pre-existing-folder layout import runs once when the catalog first opens. The shell's façades read the runtime instead of being assigned from inside features, and `LibraryStore` subscribes to ports instead of comparing generations on every change.
- Realm finding: the remote world builds on the local one (a remote video is fetched to a cache file and then read by the local metadata reader), so the remote file actions, the remote library and the originals feature are separate remote-only features, and the shared player and renderer live at the root. Only the genuinely symmetric readers and registrations are mounted twice.
- Frame suite after the migration: 163 tests, zero failures, warnings as errors (`.build/task-059-frame.log`). Tests that asserted the old persisted-tree migrations were replaced by preference-document tests; fixture capability providers became a fixed session built from `PartialRemoteSession`; provider-revocation tests now withdraw that session and assert the synchronous effect.
- **Work 8, first kernel removed.** The old `Composition` sources, their tests, the legacy preview adapter and the old fixture are deleted, and the new kernel carries the `Composition` module name. No old API name remains in either app. Complete gate after the swap: 2 release-plan tests, 48 shared, 384 RelayBar (27 optional skips), 163 Frame, zero failures (`.build/task-059-kernel-swap.log`). Frame's app product builds with warnings as errors and RelayBar's unsigned Xcode Debug target builds (`.build/task-059-frame-app.log`, `.build/task-059-xcode.log`). `git diff --check` passes. Checkpoint archive: `.build/task-059-baseline/checkpoint-kernel.tar.gz`.

- **Work 7, bridge v7.** `BridgeProtocol` is at protocol 7. `BridgeChannel` is Frame's end of a session: one connection, verified once, carrying every request by id, reporting its own end once. `BridgeSocketServer` verifies each peer once, serves each call in its own task, reports each connection that goes away, and can send connected peers a notice before ending their connections. RelayBar's broker tags each job with the connection that asked for it and releases that connection's jobs when it ends; only work with no connection behind it can still be expired by age. A status request for a job in flight is held and answered when the job changes, or after half a second with progress. `revoke()` notifies connected sessions with the reason. Frame's link makes one connection per session and withdraws when it ends; it makes no periodic request while connected, and the client no longer sleeps between status requests. The legacy English-error-string matching is removed. Frame's Info.plist declares bridge version 7.
- Transport tests (9): many requests on one connection with one identity check per peer; a slow call not delaying another; server stop ending the session at once and failing calls in flight; a client going away being reported and cancelling its calls; a notice carrying the reason; a cancelled caller's late receipt being released; v6 and v7 rejecting each other in a shape each understands; close interrupting idle connections, waiting for a running handler and allowing endpoint replacement; and a failed connection reporting no session end. Broker tests: status answered by the job finishing rather than a timer, and a connection ending cancelling its transfer at once while another session's work continues. Frame test over a real socket: RelayBar going away withdraws the session in well under a second with no request sent, local features keep their instances, a returned RelayBar gets a new connection, and Frame going away is seen by the server.

The acceptance line "at or below the Task 058 baseline snapshot" is **not met** against the pre-058 numbers. The kernel change removed the glue between the kernel and a second state machine, which is what the relays and part of the comparisons were. Most of the remaining growth is admission flags and request-staleness tokens that Task 058 added inside domain objects (`TunnelStore`, `TunnelProfileRuntime`, `RemoteFilesModel`, `LibraryStore`, the broker) so that late commands and late results are rejected after withdrawal. Tests assert that behaviour, and a kernel cannot remove it; only handing callers revocable objects would. The criterion needs the owner's decision: accept the lower counts relative to 058, or schedule that further change.
