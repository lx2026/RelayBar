# Composition and previews

Both apps are composed with the `Composition` module in `Packages/AppComposition`, built from the same checkout. `BridgeProtocol` owns the v7 wire types, the session channel and the identity contracts; `AssetGrouping` owns companion-name matching; `PreviewSupport` owns the preview registry; `MarkdownRendering` turns a Markdown document into the static page both apps show (see [Markdown preview](../modules/markdown-preview.md)); `HouseStyle` holds the palette both apps draw with and the Paper Appearance plugin (see [House style](house-style.md)). They are compiled into each app and have no separate distribution channel. `MarkdownRendering` is the only one with outside dependencies: swift-cmark, HighlighterSwift and SwiftMath, at exact versions.

The `Composition`, `HouseStyle`, `PreviewSupport`, `AssetGrouping` and `MarkdownRendering` products support macOS 13 and iOS 27. `BridgeProtocol` is macOS-only. Both platforms share the composer model and feature map layout. The Plugins window uses AppKit on macOS.

Shared grouping fixtures exercise the canonical algorithm, Frame's scanner and the fixed Python helper's listing, archive and restore path. The helper receives RelayBar's validated member list and has no grouping implementation of its own.

## Kernel

One rule governs the design: every lifetime has one owner. If the kernel owns something, nothing else tracks it; if an effect scope inside a feature owns it, the kernel does not know it exists.

- **Keys.** A service is named by a type conforming to `ServiceKey`. There are no string names.
- **Features.** A feature is a struct conforming to `Feature`. Its stored properties are its contract: `@Need` properties are required services, `@Offer` properties are slots it may fill, `@Constant` properties are values handed in by the composition root, and anything else is configuration. A feature reloads when its value changes; the wrappers always compare equal, so only configuration counts. A feature can reach nothing it did not declare.
- **Tree.** Each app has one function that returns the feature tree from its state. A feature that should not exist is not returned; there is no disabled flag. `FeatureRuntime.set` is synchronous and keeps only the latest tree, so several changes in one turn cost one comparison. An invalid tree (duplicate id, two features offering one key in one realm) is rejected and the running tree stays in force.
- **Slots.** A running feature can fill, replace and clear an offer at any time. Clearing is synchronous: before `clear` returns, every feature that depended on the value has stopped admitting work and the shell's ports no longer show it. Cleanup follows. `Slot.drained()` lets the owner wait until nothing still holds a withdrawn value before it releases that value's resources.
- **Transitions.** Each feature loads and unloads in its own task. A dependent finishes unloading before its provider's cleanup starts, and children before parents; unrelated features do not wait for each other. A feature withdrawn while still loading keeps its scope open until `run` returns, so a resource acquired late can still register its undo, which then runs at once.
- **Deadline.** A cleanup, or a cancelled load, that passes the runtime's deadline is marked stuck with the label of the effect it is waiting on. It stops holding other features up, is recorded in `diagnostics`, and returns to service when it eventually finishes. `shutdown(deadline:)` never waits longer than its deadline and returns whatever did not finish.
- **Failure.** A feature whose `run` throws is failed, with its effects undone and none of its offers published. It is retried when its configuration or one of its dependencies changes, or on `retry(id)`. Every wanted feature that is not running has a plain reason: what it needs and which feature offers that, a dependency cycle, or the failure message.
- **Ownership.** `EffectScope` is the ledger below feature level: labelled entries with a synchronous `cancel` and an awaited `undo`, owned tasks, and `run` for owned calls. Invalidation calls every cancel hook before any work is joined. `FeatureContext.perform` is the one form of check, await, check again: a result that arrives after withdrawal is never returned.
- **Realms.** A node can isolate keys for its subtree, giving that subtree a private copy of those services.
- **Ports.** `runtime.port(Key.self, realm:)` is the shell's typed, observable view of one service; `nil` means it is not available. Views never look a feature up by name.
- **Preferences.** `PreferenceStore` holds one typed, versioned document per app. An edit is validated, written atomically with the previous file kept beside it, and only then published; a failed write changes nothing downstream. A document written by a newer version is left untouched and nothing loads from it. `peek()` returns what loading would publish without loading, or nil when there is no usable saved document, so a choice can be honoured before the first window. No feature identifier is ever persisted, so adding, renaming or merging a feature needs no data migration.
- **Graph.** The runtime publishes `graph`, a `FeatureGraph`: one node per wanted feature (full id, parent, enclosing realm, phase with its reason, generation, the names of the services it needs and may offer) and one edge per need (the feature that offers it in that realm, or none, and whether a live value exists). It is rebuilt with `statuses` from the runtime's own bookkeeping and published only when it changed. `dependents(of:)` lists every wanted feature that would unload if one were removed: its descendants and the consumers of what it offers, transitively.
- **Plugins.** A plugin is a feature the person may switch off. `PluginDescriptor` gives it an id, title, one-sentence summary, symbol, default state and the feature ids it contributes. A catalog can also declare `realmRelativeFeatures`. A path such as `readers/markdown` matches beneath each nearest enclosing `FeatureNode.realm`, including nested realms. The tree’s `excluding(plugins:where:)` drops each matching subtree and can restrict a choice to one realm. The composer uses the same membership for ownership, trouble and Show on Map. `PluginChoices` stores only the choices that differ from a default, as a plain object of plugin ids, inside the app's preference document; `pin` keeps a choice even when it equals the default, for a plugin whose default is decided at launch. An app mounts a plugin's nodes from its tree function only while the plugin is enabled, so switching one is an ordinary preference edit followed by an ordinary tree change. A plugin may contribute no feature: Paper Appearance, shared by both apps, changes only how the shell draws, so each app applies the stored choice to `HousePalette` itself, when its composition is made and after every change (see [House style](house-style.md)).

## Plugins window

`CompositionUI`, shipped inside the `Composition` library product, provides the window both apps use. `PluginComposer` follows a runtime's `graph` and the app's read and write closures for plugin choices; `PluginComposerView` draws three regions:

- **Plugins.** One row per plugin with its symbol, title, summary and a switch. Show on Map is offered only for a plugin that contributes features. A failed or stuck feature of an enabled plugin shows its reason and a Retry button; "Waiting" with its reason appears only when none of the plugin's features is running. A switch shows the new state at once and reverts with a message if storing the choice fails.
- **Map.** Every wanted feature, core ones included, in columns by dependency depth with providers on the left; a child sits right of its parent. A realm is a dashed, labelled container. Plugin features carry the accent colour. Edges run from provider to consumer and stay faint until a feature is selected; an edge with no live value is dashed, and turns orange only on a selected path, because a waiting half of the tree is an ordinary state. `FeatureMapLayout` is a pure function from graph to frames. Trees wider or taller than the window scroll.
- **Inspector.** For the selected feature: id, phase and reason, each need with its provider (or that nothing offers it), each offer with its number of consumers, and for a plugin feature what else would unload with it. Selecting a feature keeps everything upstream and downstream of it at full strength and dims the rest.

Phases are shown by shape as well as colour (running, waiting, changing, failed, stuck), every node has an accessibility label with its phase and reason, and animation is dropped under Reduce Motion. Colours come from the house palette: the plugin and inspector columns on panel, the map on paper, nodes on card with line edges, ink and muted text, the running, failure and retrying tokens for the marks, and the accent colour for plugin features and selection. A plugin's summary may take four lines. Core features cannot be switched from this window.

## Mobile Plugins views

The shared SwiftUI views compile on iOS and macOS. The caller embeds `MobilePluginsList` in its Settings navigation stack and supplies group titles and optional display names for realm IDs. Groups appear in catalog order. A row opens `MobilePluginDetail`, where each mounted plugin feature shows its realm, phase, reason and full ID. Needs name the actual provider and offers count distinct consumers of that provider in the graph. Turning off a global choice lists the additional features that would unload, accounting for hosts that explicitly keep the plugin on.

`MobilePluginsWorkspace` shows the list beside a scrollable feature map and inspector. The host filter retains app-level features and enclosing realms. Selecting a node highlights its dependency paths. A plugin without a visible feature opens its detail directly. The inspector also links to its plugin detail.

The profile-backed `PluginComposer` initializer takes the stored global choice (nil for the catalog default), its writer, and two closures to read and write a `PluginHostChoice` by full realm ID. An explicit host on or off wins over the global choice. Inherit falls through to the global choice and then the plugin default. `effectiveState(for:in:)` returns the resolved Boolean and its source. The caller owns persistence and applies its updated tree. A failed write shows the storage error and leaves the controls reflecting the stored choice.

## Previews

RelayBar, Frame and mobile use the file types and limits in `PreviewSupport`. JPEG and PNG are core. More Image Formats adds BMP, GIF, HEIC, HEIF, TIFF and WebP and starts enabled in each app. Each image uses the existing image registration. Markdown, HTML and text readers allow 10 MiB, and rendered Markdown and plain text use the light and dark rules in `HouseStyle.DocumentPaper`. Website Labels uses the shared product recognition and title fallback.

`FilePreviewRegistry` registers format descriptors and render functions. A registration returns a handle; `register(_:in:)` ties it to a feature so that withdrawal removes the format at once and cleanup cancels in-flight rendering and closes every result that registration produced. Removing one format leaves the others' results open.

## RelayBar

`RelayBarComposition.tree()` returns `tunnels`, `tunnels.retry-limit`, `updates`, `updates.schedule` and `login`, `frame.host` while Open in Frame is on, plus `remote.files` while the Remote Files window is open. That node's children are one `preview.<format>` per enabled format and, while Open in Frame is on, `open-in-frame`.

- Profiles and groups are data in `TunnelStore`, which is the only owner of each `TunnelProfileRuntime`. The `tunnels` feature closes the store's command admission on withdrawal and awaits its shutdown, including bounded child reaping.
- Browser opening and the server catalog are values injected into the features that use them.
- Preferences are `preferences.json` beside the app's other Application Support files: the SSH retry limit, the automatic update check, and per-format overrides (enabled, size limit) for formats the user changed. They are imported once from `sshRetryLimit.v1` and `SUEnableAutomaticChecks`. Saved profiles, history and Frame's access grant stay in their own stores. Launch at Login reflects the macOS registration and has no stored flag.
- The retry limit and the update schedule are applied by two small features whose configuration is the setting, so a committed change reloads that feature and nothing else. Existing processes, retry deadlines and the update cycle are untouched.
- Opening or closing Remote Files is not a preference and writes nothing. A changed format toggle or limit reloads that format alone, closing the previews it produced, without replacing the window or any tunnel.
- The shell reads the tunnel store, update model, login model and window through ports. A feature that fails or is stuck is reported once through the app's alert with its id and reason.
- Quit unloads everything with a 20-second bound and logs anything that did not finish.
- Plugins: `RelayPlugins` lists Reconnect on Wake (`recovery`, on by default), Website Labels (`services`, off by default), Open in Frame (`frame`: `frame.host` and `remote.files/open-in-frame`) and Paper Appearance (`paper`, on by default, no feature). Open in Frame's default is decided once per launch: on if Frame (`com.lx2026.Frame`) is installed then, off otherwise; a choice made in the Plugins window is pinned, so it wins over that default in both directions at every later launch. The tree returns each plugin's node only while it is enabled; the choices are the `plugins` object in `preferences.json`, and a document written before plugins existed loads with every plugin at its default. Settings has a Plugins row that opens the Plugins window (1180 × 720, minimum 900 × 540); the window is not created when the app runs without windows and is closed on quit.

## Frame

`FrameComposition.tree()` returns the local world at the root and the same media features again inside the `remote` realm.

- Root: `access` (security-scoped folders), `library.catalog`, `library.favorites` and `library.scanning` once the SwiftData catalog is open, `files.trash`, `files.archive`, `files.export`, the shared `playback` player and `documents` renderer, and the media nodes below.
- Media nodes, mounted at the root and in the realm: `thumbnails`, `metadata`, `previews`, one `preview.<format>` per enabled format, and `playback.video`. They are written once against `MediaSource`; the realm isolates `MediaSource`, `Thumbnails`, `Metadata`, `Previews` and `PlaybackPreviews`.
- `relay.link`, present while remote folders are shown, owns discovery and the session and offers `RelaySession` through a slot. Each session is one authenticated connection. It fills the slot when a catalog request on a new connection succeeds and clears it when that connection ends or RelayBar names a session failure: quitting, revocation, an incompatible version or transport loss. The ended session's client is released only after everything that used it has finished unloading.
- `remote/source` needs `RelaySession`, so the whole realm loads with a session and unloads without one: `remote/library`, `remote/thumbnails`, `remote/metadata`, `remote/metadata-helper`, `remote/originals`, the remote preview formats, and `remote/delete`, `remote/archive`, `remote/export`. Local features are unaffected. A disconnected remote document keeps its rendered page and stops reading; Retry reconnects. Reconnection never repeats a mutation.
- `remote.access` is the shell's owned access to the session: a call made through it is joined before the session is released, and a late result is rejected.
- Preferences are `preferences.json` in the app's Application Support directory: display preferences (media Info, remote folders, Subfolders, thumbnail width, per-root layout) and per-format overrides. They are imported once from the legacy UserDefaults values; pre-existing folders are given the contact-sheet layout once, when the catalog first opens. Bookmarks, favourites, hidden recents and window state keep their own stores.
- The shell reads feature objects through the runtime; nothing is mirrored by hand. Session Trash history is data owned by the composition and survives any reload of the Trash feature.
- A fixed session can be mounted in place of the link for fixtures and the verification bundle.
- Plugins: `FramePlugins` lists Prompt Search (`prompt-search`, on by default) and Paper Appearance (`paper`, on by default, no feature; applied when `FrameComposition` is made, before Frame's window). While it is enabled its node is one of the media nodes, so it is mounted at the root and again in the realm, where `PromptSearch` is one of the isolated keys. The choices are the `plugins` object in `preferences.json`; an older document loads with defaults. The app menu's Plugins… item opens the Plugins window.

The session channel and RelayBar's per-connection job ownership are described in [Frame viewer](../modules/frame-viewer.md). Task 059's verification record is [here](../../verification/059-single-owner-composition.md). Native, signed and live-host acceptance remain with Task 058; installed builds have not been updated.

RelayBar mobile supplies its catalog, group names, host labels and preference writers to the shared composer. The optional mobile detail supplement displays app-owned controls inside the selected plugin detail in either layout, including overrides for saved hosts without a mounted realm and the host network’s remembered destinations. The mobile host shell can supply a scene-local house form so simultaneous host workspaces honour independent Paper Appearance overrides.
