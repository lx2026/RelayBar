# Composable architecture for RelayBar and Frame

Status: In progress — 2026-11-07

[Task 059](059-single-owner-composition.md) supersedes the kernel design below where they conflict: per-profile and per-group loader entries, the persisted configuration tree, typed events, policy metadata and kernel-only dependency resolution. The monorepo, distribution, native and live-host requirements here still apply.

## Outcome

Consolidate RelayBar and Frame in the existing `lx2026/RelayBar` monorepo and refactor both into feature trees managed by one shared Swift composition kernel. Features declare required services, own their resources, and load or unload as dependencies change. Complete all six phases of the supplied *Composing RelayBar and Frame* proposal, including remaining features and Settings, while preserving independent app distribution.

## Delivery Boundary

- Import the sibling Frame project from the previous Frame working folder into the existing RelayBar repository. Keep its GitHub name/URL, history, issues and published releases. This is the canonical cross-app task; the imported Frame task index links here.
- Baseline is current local source: RelayBar 1.6.0/20, Frame 0.1.0/15, bridge v6, including HTML and document workspaces. The proposal's v5 examples and older consent model are historical, not requirements to restore.
- Keep separate apps, processes, sandbox postures and release trains. Preserve supported OS versions, workflows, stored profiles, bookmarks, favorites, history, resource limits and current access policy. Frame remains history-neutral; RelayBar owns SSH.
- Target layout: `Apps/RelayBar/`, `Apps/Frame/`, `Packages/AppComposition/`. Shared app-neutral kernel, bridge protocol, grouping and preview-support modules use local Swift package dependencies in the same checkout. No separate shared-code repository, package publication or Cordis runtime dependency is required.
- Keep separate app versions, build numbers, signing identities, archives and release notes. RelayBar retains `v*` tags and `RelayBar.zip`; Frame uses `frame-v*` tags and `Frame.zip`. Shared code is bundled into each app; users install no separate package and neither app automatically installs the other.
- Preserve `brew install --cask lx2026/tap/relaybar`, `brew upgrade --cask lx2026/tap/relaybar`, the separate `lx2026/homebrew-tap` repository, versioned download URLs, and RelayBar's signed Sparkle feed at `https://lx2026.github.io/RelayBar/appcast.xml`. Keep update-signing continuity and the existing GitHub Pages site. A future Frame cask/update feed is separate release work.
- Migrate incrementally; each phase leaves both apps buildable and usable. No runtime code loading, third-party plugin platform or release-version change is included. A plugin is a statically linked feature with a managed lifecycle.
- Work stays local until explicitly authorized: no pushes (including tags), GitHub releases, artifact uploads, distribution notarization, or production website/feed/Homebrew changes. Completion does not authorize any remote publication.

## Work

1. **Establish the monorepo and extract shared contracts.** Record both source baselines; import Frame and relocate app sources without discarding local work or rewriting existing RelayBar history. Exclude credentials, generated bundles and caches. Move duplicated wire types, socket/identity support and Swift companion grouping into canonical modules without changing wire v6 behavior. Update SwiftPM, Xcode, scripts, documentation links and CI for the layout; a single checkout must build both apps. Remove mirrored-source checks and verify the fixed Python helper's grouping against shared fixtures, including independent Markdown/HTML files. Shared-module changes test both apps. Keep release preparation selectable per app and remote publication explicitly gated. Preserve the [existing distribution contract](../system-specs/operations/build-and-release.md); Frame releases must not replace RelayBar as the repository's GitHub “Latest” release, and download/update consumers use app-specific versions or feeds.

2. **Implement the kernel.** Add typed service keys, declared requirements/provisions, child contexts, lifecycle instances, synchronous/asynchronous effects, isolated service scopes, per-call policy metadata and a configuration-tree loader. Support typed notification, parallel, serial, bail and waterfall events. Track owned tasks, observers, timers, processes, sockets and temporary resources through explicit disposers. Serialize lifecycle transitions across suspension points; actor isolation alone is insufficient. Withdraw providers before draining dependents, dispose dependents/children first and effects in reverse order, roll back partial activation, reject undeclared access and stale callbacks, and expose pending/failure reasons. Provider identity changes restart consumers; policy-only changes do not. Diagnose cycles and conflicting providers. Reconciliation must settle to the same active bindings as a cold load of the final valid tree.

3. **Migrate previews first.** Introduce a shared preview registry and convert both apps' existing image, Markdown, HTML, JSON/text and video paths into plugins as supported by each app. Share contracts/resource policy while retaining native rendering adapters. Loader-backed toggles and limits must remove registrations, listeners, renderers and owned work at runtime. Preserve keyboard focus, online-resource policy, bounded relative-resource loading and media behavior.

4. **Compose the bridge in both directions.** RelayBar's host plugin owns the broker; Frame's link plugin publishes authenticated, versioned `relay.*.v6` capabilities. Remote library, thumbnails, documents and actions consume only their required capabilities; optional helper availability must not gate unrelated viewing. RelayBar's Open in Frame integration consumes a viewer capability. Keep discovery/launch separate from an authenticated session so either app can start first and handoff can launch Frame. Route quit, revoke, hidden remote folders, disconnect and incompatibility through capability withdrawal, with pending/retry presentation and reactivation. Preserve the last-good document on transient disconnect without retaining remote authority. Replace duplicate UI teardown paths, not audit-token checks, nonce validation or provider-side authorization. Policy metadata reflects existing grants and is enforced per call; it adds no consent prompts.

5. **Migrate tunnels and Remote Files.** Give each profile a lifecycle instance and each group a loader entry; isolate each Remote Files window/session. Move launch, retries, control operations, transfers and retirement under owned effects. Preserve generation protection, group-edit continuity, retry budgets, cancellation, bounded child reaping and deferred app termination from the [process-lifecycle contract](../system-specs/modules/process-lifecycle.md). Retain operation identities wherever necessary; a disposer alone does not prevent late process completions.

6. **Complete both feature trees.** Migrate remaining RelayBar catalog/history, browser launch, updates and login, and Frame local library, scanning, thumbnails/metadata, playback, favorites, Archive/Restore, Delete/Trash and export. Use one plugin per user-visible feature and separate directed integrations to avoid cycles; pure algorithms remain libraries. Reduce app shells to composition and presentation, removing cross-feature singleton access and parallel lifecycle machinery. Persist a versioned configuration tree atomically; Settings edits its feature flags/configuration without exposing internal architecture. Migrate existing preferences once with rollback, retaining domain stores and security-sensitive grants separately. Document adding/removing a feature through its package and tree entry.
